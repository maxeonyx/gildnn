# Background experiment execution — don't block the agent on training runs

Following on from the earlier dictation about multiple in-flight workstreams. The specific problem is that blocking on a training run wastes all that agent time — a three-hour experiment wastes three hours that could be spent on theory work, small experiments, process improvement, integration, research, anything that doesn't use the GPU heavily.

Experiments should be launched in the background somehow, so the launch returns immediately with something to track it — a process ID or some kind of handle. The agent keeps a record of what's running — in `runs/` or similar — with the PID, what experiment it is, when it started, where the logs are. Then it continues doing other useful work and checks back periodically.

The ratio of GPU time to agent thinking time should not be one-to-one. The GPU can be saturated with a long run while the agent is doing everything else.

## Subagent instruction requirement

This needs to be explicitly told to the subagent — it will not do this by default. If the run is expected to take more than around five minutes, the subagent should launch it in the background, then stop and return. The subagent's final message should be something like: "I have started the experiment. PID is X, logs at Y. Stopping here as requested — please resume me when you want to check on it."

The subagent launches, reports the handle, and stops. It doesn't poll, doesn't wait, doesn't keep going. The orchestrator resumes it later when it's ready to check.
