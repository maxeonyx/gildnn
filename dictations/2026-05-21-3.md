# Background experiment execution — don't block the agent on training runs

Following on from the earlier dictation about multiple in-flight workstreams. The specific problem I want addressed is that the agent is currently running training experiments directly in a PowerShell tool call, which blocks the entire session for the duration of the run. A three-hour experiment wastes three hours of agent time that could be spent on theory work, small experiments, process improvement, integration, research — anything that doesn't need the GPU heavily.

The process needs to change so that training runs are launched in the background and immediately return a process ID or some kind of handle. The agent then continues doing other useful work and periodically checks on the run's status. Don't run experiments by blocking on a PowerShell command. Use something like `Start-Process` with `-PassThru` to get a process object, or redirect output to a log file and return immediately, or whatever the right Windows equivalent is. The point is: launch and continue, don't launch and wait.

The agent should maintain some kind of record of what's running — a lock file or a simple note in `runs/` — with the PID, what experiment it is, when it started, and where the logs are. Then it can check back periodically without blocking.

This is important. The ratio of GPU time to agent thinking time should not be one-to-one. The GPU can be saturated with a long run while the agent is doing everything else.
