## Embedding-space prediction (no output projection)

I think in my vision, we don't have a projection before the logits. Actually, this bears in mind an interesting question. Is there another way we can frame the cross-entropy loss so that we don't need a projection into a one-hot? Rather, can we, let's say, put all of the embeddings in some kind of space, predict a point in that space, and allow the cosine distances or something like that to be the logits? Can we represent a distribution via a point in a high-dimensional space that is specifically chosen based on its distances from the embedding points?

There's one reason I like this idea, which is that I can have as many embeddings as I want in my space, no matter how many dimensions it is. It gives me a worse and worse representation of a distribution the more and more embeddings I have in my space beyond the number of dimensions I have. But if it's somehow possible to make it approximately a distribution and we can do approximate Wasserstein and approximate Bayesian updates on it, then I'm happy with it because I can shove loads of tokens in there without having that many dimensions and without having a projection. So I can use it for my interfaces between my blocks and for my output.

## Combining blocks

Block zero produces logits, right? What is the dumb mechanism that combines block zero's output and block one's output that means block zero doesn't have to model the low frequency long time scale information?

With weight-tied dot-product readout, addition in embedding space IS the Bayesian product of distributions — that's the inter-block combination mechanism. No learned combiner needed. Block 1 just needs to be a good independent predictor from its own perspective and the addition does the right thing.

## Timing and parallel execution

The problem is: block zero takes one time step to produce its outputs, and then block one is therefore dependent on block zero and we're back to a sequential architecture in disguise. By the time block zero produces its output there's a new input, and those both go to block one, at which point block one is processing the first token and has produced its output. We can have sequential dependencies across time steps only.

## Noise on laterals

I think we add noise at each step. I think we add noise with the laterals. Even just a tiny amount of noise. The question is when the input comes in and it propagates laterally before it gets processed, because processing adds one delay, then what is the input? Is it a noisier and noisier sample? But the noise is like iteratively added. So the raw input gets less and less certain and the neighbour's outputs get more and more certain in comparison.

The noise creates the information hierarchy. Block zero receives the raw token. Block one receives the raw token plus one noise step — that's true. And block two, token info plus two noise steps — that's true, right? However on the next time step block two would not receive raw token plus two noise steps. Well it technically would but it would also receive block zero's output and block one's output and block zero's output would have one noise step added, block one's output would have two noise steps added. Also, I think block zero should probably have noise added before it receives the input.

So distant blocks can't rely on precise token-level information — it's been drowned out. They're forced to extract slower/more abstract features from the accumulated noisy evidence. Meanwhile their own internal state, computed over many timesteps, gets more refined. The noise isn't a hack — it's what forces the timescale separation without having to design it in.

## Avoiding activation growth from noise

The problem with noise is that it just means the activations get bigger, so we have to avoid that somehow. Normalization's kind of annoying but sure, that's the MVP for this. Normalize after adding noise — activations don't grow, but noise still corrupts low-energy features while preserving high-energy ones. Only robust high-SNR features survive multiple hops.

Ideally it would constrain to some kind of distribution. Some kind of mix of distributions, I don't know. But normalize for now.

## Key findings from the think agent

- Dot-product against token embeddings is basically standard weight tying — not exotic
- With normalized embeddings + dot-product logits, adding points IS the Bayesian update (combining distributions by multiplication). That's the inter-block mechanism for free.
- You can have more tokens than dimensions — it's a rank-limited log-linear family, not arbitrary distributions, but it still works if next-token distributions live near that manifold
- The simplest version: normalize token embeddings (unit sphere), block output = point in that space, logits = dot product / temperature, combine laterals by addition, local loss = cosine or L2 between points
