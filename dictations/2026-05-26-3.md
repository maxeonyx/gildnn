# 2026-05-26-3

No inertia. Think from first principles about what's best for us, don't default to what we were doing before or what other people are doing. We need to compare against others to stay grounded, but we shouldn't just be doing what everyone else is doing.

## Synthetic tasks

I don't know what the right synthetic task is — it needs investigation. But a synthetic dataset solves some problems. For example, it won't be overparameterized — we can have a dataset that won't even be fully learned, so we can actually see whether architectural changes matter without the overfitting confound.

CFG/grammar tasks seem interesting because they're more like programming languages — strict nesting, hierarchical structure. But I'm not prescribing that specifically.

## Don't run longer than you need to

Don't waste an extra two hours running a three-hour run when the first hour would have proved what you wanted. Don't waste fifty minutes when the first ten minutes would have proved what you wanted. You're not trying to run the whole epoch or the whole dataset — that's just redundant once you have your answer.

## No standard dataset

There shouldn't be a single "standard dataset" for this project. One of the explicit purposes is that we can run whatever architecture we come up with across multiple datasets and tasks. Character-level language modelling is a fine task for now. But I'd like to see image patch sequences and other tasks later on.

## Baselines

For every dataset and every run length there should be a baseline. Baselines should be recorded. But that doesn't mean every baseline needs to be run on every dataset — only that in order to compare, you need a baseline. If you're running a mechanism test on a new task or a new run length, run the baseline too so you have something to compare against.

## Graduated complexity

The key property I want: a task where the data isn't the bottleneck, so architectural differences are visible. Use the smallest training configuration that proves the mechanism — including dataset size/complexity.

## Build up from pieces, don't test the whole assembly

Don't test the entire assembled system in one go. Break it into pieces, test the pieces individually, attach two pieces together, test the attachment, then build up pieces into chunks and the final thing out of the chunks.

For example with local predictive loss: don't jump to "2-block model with local loss + mixing + topology" as the first experiment. That has too many confounds. Instead: verify the prediction objective works in isolation (30 seconds), verify the mixing doesn't destroy signal (30 seconds), then combine them.

The current local_predictive experiment has too many interacting variables to learn much from — hard-coded 50/50 mixing, MSE on raw activations, the topology, the prediction target choice. Any one of these could be the problem. Break it down.

## Optimize the feedback loop

Every time the agent completes an experiment cycle (run → analyze → decide next), it should ask: how could I have done that faster? How can I get the same experimental result with better experimental design, better adherence to my goals, and less wall clock time?

The agent should be optimizing its experimental process more and more over time — speeding up the feedback loop, not just executing the same 22-minute cycle repeatedly. If a 2-minute run on a simpler task would have answered the same question, that's what should have happened. The process should get tighter, not stay static.
