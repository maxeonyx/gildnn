# Architecture clarification: the model is a cellular automaton

The model is a cellular automaton. A message-passing graph. There is no state at all. Blocks are absolutely one hundred percent stateless.

The token information flows out and it doesn't go back. Only the predictions go back.

The structure:
- Each **node** is a combining function
- Each **through-time, in-place edge** (vertical) is a block — stateless feedforward
- Each **left-right edge** (lateral) is propagation, which adds noise

Information just bounces around between blocks over time. Higher-level blocks have context from further back at a given timestep, because the outputs of blocks lower in the chain get merged onto the stream and flow rightwards. None of this makes sense unless we are doing multiple timesteps and propagating information out with delay across many, many timesteps. Timesteps not equal to tokens — for one token we might have many timesteps.

The noise on laterals is what creates the need for prediction and the information hierarchy.

## Delete ParallelDiagonalModel, start from scratch

"ParallelDiagonalModel" is not a phrase I ever used until an agent used it. Delete it. It implements the wrong thing — it's an RNN with carry state, GRUs, temporal attention. That's not my architecture.

Start from scratch. Build a model that actually matches my architecture: the cellular automaton grid with stateless blocks, lateral propagation with noise, many timesteps per token, many blocks, information bouncing around over time. The pieces that have been validated (W₂² loss, combining functions) can inform the design, but the model code itself starts fresh.

## What the loop should be doing

The piece tests are done. I don't want to see two-block toy experiments. Two blocks doesn't test anything. Sequence lengths of four, of thirty-two don't test anything.

I want to see something that looks like the model I'm trying to get to: many blocks, many timescales, optional number of steps per token, delayed information propagation, training on long sequences. Scale it up. If there are unproven pieces that would make the result indeterminate, tell me what they are — don't just keep running ablations without saying why.

## Daily/weekly report format (for the loop agent)

When writing daily and weekly reports, back-chain from the goal:
- Why is the model not yet doing the full architecture?
- If it did the full architecture now, what would happen?
- Why would that result be indeterminate or built on shaky foundations?
- Therefore it's doing this step
- Therefore it's doing that step

At every step, justify why we're not just running the real thing. If you can't justify it, we should be running the real thing.
