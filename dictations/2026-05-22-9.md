## The original prompt (verbatim, sent to a mechanic)

```
You are implementing a new experiment for an ML research project. The goal: test whether blocks running on fixed schedules (not every timestep) can save wall-clock time without hurting quality.

## Context

The project has a "residual stream across time" architecture — a recurrent model that processes one timestep at a time, applying blocks to a shared residual stream. Currently there's only ONE feedforward block per timestep. The new idea: have MULTIPLE blocks, each assigned a fixed execution RATE (every N timesteps). When a block doesn't execute, its last output is reused (stale read). No gating — the schedule is hardcoded.

Prior results show:
- Stale reads barely affect quality (+0.005 nats)
- Dynamic gating (learned skip decisions) made things SLOWER due to gating overhead
- CUDA stream parallelism doesn't help on single GPU

So this is the simplest version: just don't run some blocks on some timesteps.

## Architecture

Based on `experiments/residual_stream_time_mixadd/model.py` (read it for the MixAdd and TemporalWindowAttention components). The new model:

- Multiple `ResidualFeedForwardBlock` instances (say 4 blocks)
- Each block has a `rate` parameter: rate=1 executes every timestep, rate=2 every 2nd, rate=4 every 4th
- On skipped timesteps, a block's contribution is its cached last output
- Temporal attention still runs every timestep (it's cheap relative to feedforward blocks)
- MixAdd for residual combination

## What to build

Create `experiments/fixed_multi_rate/__init__.py` and `experiments/fixed_multi_rate/run.py`.

The experiment runs TWO models side-by-side:
1. **All-rate-1** (control): 4 blocks, all rate=1 (execute every timestep)
2. **Multi-rate**: 4 blocks with rates [1, 1, 2, 4] (blocks 2 and 3 skip some timesteps)

Both must have the SAME parameters (same weights at init). Only execution frequency differs.

## Training setup

- d_model = 128, feedforward_dim = 256, temporal_window = 4, num_heads = 4

- Evaluate every 500 steps: val loss AND wall-clock time per 1000 forward passes

## Experiment ladder

## Measuring wall-clock

After training, measure forward-pass time:
- Run 100 warmup forward passes (no grad)
- Time 1000 forward passes with `torch.cuda.synchronize()` before/after
- Report ms/batch for both models
- The multi-rate model should be measurably faster (fewer block executions)
```

## What's wrong with this prompt — annotated

**Context section:** Relies on the prompt to explain the idea. The prompt is small and the idea is big. Better to write a durable document explaining the question and reference it. That way we also have notes that persist across sessions. If the agent dies or hands over, this context is lost.

**Architecture section:** Same deal, although this one's relatively brief. Still, if it were in a durable doc, a different agent could pick it up without being re-prompted.

**"What to build" section:** This shouldn't need to be in every prompt. There should be durable conventions (AGENTS.md) explaining where things go and how experiments are structured. The parent shouldn't be dictating file names — the implementation agent should decide based on conventions and pre-existing patterns. Over-specifying file names means the parent is doing the mechanic's job.

**Training setup:** Overly detailed. The mechanic can look at prior experiments for hyperparameter conventions. If there's something specific about this experiment, say that one thing. Don't repeat all the defaults.

**Experiment ladder:** Good idea. Under-explained. The ladder should be documented somewhere durable and the sub-agent told to read it. The parent's job is to say what rung we're on, not re-explain the ladder.

**Measuring wall-clock:** Good. But the goal is what matters, not the procedure. The agent should know how to measure things — tell it the goal ("prove wall-clock speedup") and let it figure out the measurement procedure. Some of this is obvious to a competent implementation agent.

**Key implementation detail:** Probably fine to include, but again should be in the question doc for durability. It would be nice to have a dated record of the details of each experiment and what it was trying to get out of it.

**Verification — "Run the experiment, report":** This is explicitly the anti-pattern. Instead we need to guide on the meta level of process: set up the experiment, report back, launch in background and report back, I will resume you later.

**Environment section:** Basic stuff that should be in AGENTS.md. It's injected into context by default, so mentioning it is unnecessary. Wasted tokens.

## The corrected pattern

The right approach has several components:

### 1. A durable question doc (written before delegation)

Write `research/questions/fixed-multi-rate/README.md` explaining: context, question, hypotheses, what steps will be involved, what the goal is. This persists across sessions.

### 2. Improvements to AGENTS.md and conventions

Environment, file naming conventions, how to run things — these go in AGENTS.md and never need repeating.

### 3. The first prompt (references docs, explains process)

Big, but mostly references:

```
Read `research/questions/fixed-multi-rate/README.md` for the question, hypotheses, and architecture.

Your job: implement this experiment. Follow the ladder in PROCESS.md.

Set up the experiment — code, model, data loading, training script. When it's ready to run, STOP and report back with what you're about to run and how long you expect it to take. Do not run anything yet.
```

Why reference instead of saying directly? Because the question doc persists. If the agent dies mid-task, a new agent can read the same doc. If the parent needs to delegate again, it doesn't need to re-explain everything. Prompt content is ephemeral — durable docs are infrastructure.

### 4. The second prompt (tiny — parent decides based on the report)

```
Go ahead. Launch it in the background. Return the PID and log path. Stop immediately.
```

### 5. The third prompt (conditional — checking results)

```
The run should be done. Check the log at [path].

If it succeeded: report results. Include a sanity check — extract one example from the dataset, one prediction from the trained model, verify they look reasonable for the loss level achieved. Include these examples in your report.

If it failed or needs to be rerun: tell me what went wrong and what you'd change. Do NOT relaunch without reporting back first.
```

### Why this up-down-up-down pattern?

Each "report back" is a natural checkpoint where the parent can:
- Do other work while the GPU is busy
- Course-correct if something's wrong
- Maintain visibility into what's happening

What happens if we don't do this? The mechanic runs the full experiment soup-to-nuts, takes 30 minutes, the parent sits idle the whole time, Max has no visibility, and if something goes wrong at minute 25 we've wasted the whole session.

### What needs to happen

Put this entire pattern into a durable document explaining to the parent agent how subagent delegation should work. Make sure PROCESS.md and the loop prompt reference this document. The parent agent must read it before delegating any experiment work.
