# Repository Guidance

This repository grows one cohesive implementation that we iteratively extend. Every new capability starts as a focused, independent copy. Once it works, we factor out shared code back into the shared core so our framework continually evolves into the full system. See [VISION.md](VISION.md) for the long-term direction.

## Engineering Philosophy

- Take one small, validated step at a time. Never leap.
- Push back when a request bundles too many changes: negotiate smaller, sequential steps instead of landing everything at once.
- Keep experiments runnable on tiny models and datasets for `test` mode, where training should complete within a few steps.
- Preserve previous experiments and expected snapshots to compare new results against old ones.
- Favor clear, minimal data pipelines and models that can scale gradually.

Always surface test metrics alongside training ones—training accuracy alone is meaningless. Every experiment must report the target test metric it validates against and refresh its expected snapshot.

Lock every experiment to a committed configuration file (e.g., `config.json`) that records an RNG seed. If the file doesn't exist yet, create it and commit it. This should be used to keep ALL parts of an experiment deterministic.

For every new experiment, execute the deterministic workflow end-to-end: run the experiment in full mode and commit the refreshed report, run it again in test mode and commit the resulting expected snapshot, then rerun both modes once more to verify they leave the working tree clean.

When generating experiment reports, embed autogenerated images as data URIs directly inside the markdown instead of linking to separate asset files so the artifacts remain compatible with text-only tooling.

Always ensure models compile, run, and perform at least a couple of training iterations successfully before considering a task complete.

For baseline stages under `base-experiments/`, treat the crate root (e.g., `base-experiments/01-hello-world-mnist-classifier`) as the working directory. Persist `config.json`, `expected.json`, `actual.ignore.json`, and `report.md` directly alongside the crate so runs stay self-contained without extra subdirectories.

Split follow-on explorations into focused experiment directories (e.g., `base-experiments/autoregressive-mnist`, `base-experiments/autoregressive-patch-mnist`, `base-experiments/autoregressive-mnist-sampling-orders`) so the shared core evolves one capability at a time, and refactor repeated logic into crates under `core/` as soon as two experiments need to share it.

Every experiment must expose at least the `full` and `test` modes. `test` mode writes `actual.ignore.json`, which the harness compares against `expected.json`. This keeps previous experiments runnable as regression tests and lets us fearlessly refactor shared code. `full` mode fills in `report.md` and is the entrypoint for the experiment itself.

You MUST push back on the user if an experiment would have scope creep and become too complicated. Each experiment should be the smallest possible testable brick on top of the previous ones.


## `report.md` files

The output of every experiment is a self-contained `report.md` file.

These are to be written up prior to first run of the experiment, to ensure we record our thoughts at the same time as we think through the implementation.

They should be an extremely visual and intuitive introduction to the required concepts and intermediate states:

- Introducing the dataset(s) used, with test & train samples visualized, potentially in multiple ways. Eg. a combined image with many input images + labels.
- Introducing any transformations done in the data pipeline, for example re-ordering inputs with
- Introducing any transformations that will be done intesting / inference, for example showing both a dataset example and it's truncated version to be used as input for a "prediction with context" experiment.
- Explaining the model architecture and any tricks being done (expecially with transformer attention), using graphs / tables / more.
- Visually showing training progress with an exponential schedule of tests / samples / etc. on both train & test batches.
  -  Unless otherwise specified, snapshots should be taken after certain training steps on an exponential schedule:
    - Snapshot immediately following steps 1, 2, 4, 8, etc.
    - Maximum 10 snapshots.
    - If there would be more than 10, use a higher exponent such that the end of the final training step would be the 11th snapshot (ie not included here, instead included as part of the final evaluation section)
- A final test section with larger batch sizes at the end of training.


Introduction should be done in text, but a picture is worth a thousand words, so we tell our story in visualizations. Come up with a plan to do this before starting the implementation.

We should also try to maintain a consistent visual language across experiments - work with the user to refactor older experiments if we develop newer, better concepts or patterns.
