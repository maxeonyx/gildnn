# 2026-05-20

Two threads closed tonight. The predictive chain question has a clean answer. The dynamic depth question opened something worth pursuing.

## Predictive chain: the bottleneck hypothesis is wrong, the chain's advantage is gone at scale

The chain has been beating baselines on small-data Shakespeare (val loss ~2.59 vs transformer ~2.84, RNN ~2.95). The open question was why. The bottleneck hypothesis — that the narrow message channel `message_dim=24` was the actual regularizer — was the most obvious candidate.

**Bottleneck ablation.** Removing the bottleneck (`message_dim` 24→96) gave val loss 2.564, essentially unchanged from 2.593 with the bottleneck. The bottleneck is not the mechanism.

```json
// shakespeare_no_bottleneck/comparison_summary.json
{
  "val_loss": 2.5639562606811523,
  "val_accuracy": 0.2926136553287506,
  "parameter_count": 35118
}
```

**Graph topology.** An 8-node order-2 skip DAG was tested with both uniform aggregation and learned attention. Both were worse than the linear chain:

```
graph_skip2_uniform_aux_1_detach: val_loss = 2.794
graph_skip2_attention_aux_1_detach: val_loss = 2.842
historical chain baseline: val_loss = 2.593
```

Learned attention did develop nontrivial weights on the overfit set (max deviation from uniform reaching 0.47–0.50 across nodes) but this didn't translate to better generalization. The graph variants overfit harder — wider connectivity gives the model more ways to memorize, not fewer.

**Context scaling** (5→10→20 chars). Chain wins at all three sizes:

```
context_size | chain  | transformer | rnn
      5      | 2.594  |    2.843    | 2.948
     10      | 2.565  |    2.922    | 2.972
     20      | 2.634  |    2.954    | 2.915
```

The chain's advantage doesn't grow monotonically with context — at context=20 it actually pulls back slightly. But the advantage is present and stable across all three, not a fluke of one configuration.

**Scale-up** (100K chars, ~200K params, context=32, 5000 steps). The chain's advantage disappears:

```
// scale_up/val_loss_table.txt
model          params    train_loss  val_loss  val_acc
rnn            195605    1.5036      1.7269    0.5034
transformer    186805    1.3124      1.7310    0.4970
predictive_chain 203461  1.3895      1.7345    0.5063
feedforward    187445    0.6607      3.7712    0.3514
```

RNN 1.727, transformer 1.731, chain 1.735 — all within noise. The chain is 10–80× slower.

The conclusion is unambiguous: the chain's advantage is a regularization effect from the sequential bottleneck. With scarce data and small models, forcing information through a narrow sequential channel prevents overfitting in a way that unconstrained architectures fail to match at the same parameter count. With enough data, the regularization is unnecessary and the speed penalty is just a penalty.

The predictive-chain question is closed. The next discriminating question is whether the underlying idea — sequential inductive bias — has any value at a scale where data isn't the binding constraint, or whether the interesting property is really just "narrow bottleneck regularizer." That's a different experiment.

## Dynamic depth: the routing signal works, the halting criterion doesn't generalize

A weight-shared GRU applied 1–8 times per token, with a loss-prediction head trained to estimate task loss at each depth. At inference, the head halts when predicted loss is below a threshold.

Multi-exit training is stable. The depth distribution on the training set is heavily right-skewed:

```json
// comparison_summary.json — dynamic_depth, train depth_histogram
{
  "1": 4132,
  "2": 1102,
  "3": 258,
  "4": 95,
  "5": 28,
  "6": 12,
  "7": 5,
  "8": 6
}
```

Mean used depth 1.38 on training, 1.35 on val. The model allocates deeper computation to harder tokens. From [`depth_annotation.txt`](../questions/dynamic-depth/artifacts/depth_annotation.txt) — the format is `<char><depth>`:

```
i2 d1 e1 ,1 ↵1 H1 o1 l1 d4 ...
```

The hardest tokens by used depth (from `comparison_summary.json`):

```
context        | target | used_depth | actual_loss
"ataracts a"   |  n     |     6      |   0.217
"se blood i"   |  s     |     5      |   5.823
"ard the br"   |  e     |     5      |   5.766
"s, and cra"   |  c     |     5      |   1.767
```

Tokens like the `n` in "cataracts" (completing a rare compound word) get maximum depth. Some hard tokens get high depth and still fail — `target=s, loss=5.82` at depth 5. The routing is content-sensitive and plausible.

The quality comparison at val:

```json
// comparison_summary.json — val_metrics task_loss
fixed_depth_1:   4.348
fixed_depth_8:   4.066
dynamic_depth:   4.385
```

Dynamic depth is marginally worse than fixed-8 on val task loss (4.385 vs 4.066), despite using only ~1.35 mean depth vs 8. The loss-prediction head has high val MSE:

```json
"loss_prediction_loss": {
  "fixed_depth_8 val":  28.25,
  "dynamic_depth val":  32.20,
  "fixed_depth_1 val":  34.19
}
```

The head learns to predict task loss on the training distribution but doesn't generalize precisely enough to val. The halting threshold was set from train statistics (`halting_threshold = 0.4011`, the train task loss of fixed_depth_8), so the criterion is calibrated on an overfit model. That's the obvious confound.

What's real: the model does allocate computation non-uniformly and the allocation is semantically meaningful. What's not established: whether the halting criterion is genuinely effective for generalization, or just approximately tracking difficulty in a way that breaks under distribution shift.

The next discriminating step is to calibrate the halting threshold on a held-out sample (not train loss), or switch to a learnable scalar threshold that's jointly optimized on val. If the loss-prediction head is the bottleneck, fixing its calibration would be cheap to test.

## Dynamic depth improved: calibration works at scale, position-in-word dominates

Scaling to 100K chars and sweeping thresholds for a Pareto frontier:

```
Large corpus Pareto frontier (threshold → val_loss, avg_depth):
 val_loss  avg_depth  compute_savings
 1.722     8.0        0% (baseline)
 1.730     5.7        29%
 1.738     4.56       43%  ← recommended
 1.755     3.16       60%
 1.786     1.30       84%
```

**43% compute reduction for 1% quality loss.** The loss-prediction head calibrates dramatically better at scale — correlation 0.50 on val (was 0.08 on the 7K corpus), MSE drops from 33 to 1.9.

### What "hard" actually means

Systematic feature analysis on the large-corpus model:

| Rank | Feature | Effect Size | Direction |
|---|---|---|---|
| 1 | Position in word | η = 0.46 | Word-initial = depth 8, mid/end = depth 3.8–4.5 |
| 2 | Character identity | η = 0.37 | Uppercase rare letters deepest |
| 3 | After punctuation | r = −0.23 | Post-punctuation is *shallow* |
| 4 | Bigram novelty | ρ = −0.19 | Novel bigrams shallower |
| 5 | Word frequency | ρ = 0.16 | Rare words slightly deeper |
| 6 | Local entropy | ρ = −0.12 | Weak effect |

The model spends its depth budget almost entirely at **word boundaries**. First character after a space gets depth 8.0 uniformly — this is where the model must commit to a word identity. Mid-word and end-of-word positions coast at depth 3.8–4.5. Post-punctuation tokens (newlines, spaces after periods) are among the shallowest — these are high-certainty positions in Shakespeare (new line = character name is coming).

This is a clean mechanistic story: the model thinks before speaking. Once committed to a word, continuation is cheap.

⚠️ Reproducibility caveat: the analysis used a retrained model (same hyperparams, different seed). The position-in-word dominance is robust; fine-grained character-level patterns differ between seeds.

See [`research/questions/dynamic-depth/artifacts/improved/depth_analysis/analysis.md`](../questions/dynamic-depth/artifacts/improved/depth_analysis/analysis.md).

## Architecture reframe: modules are residual blocks on a shared stream, not recurrent stacks

Dictation [`2026-05-20-10`](../../dictations/2026-05-20-10.md) clarified what the architecture should actually be: each module is a single residual block operating on a shared `d_model` stream, not a recurrent mini-stack with its own hidden state. The experiments run earlier today (local-learning, predictive-chain, chain-dynamic-depth) were built on the old recurrent interpretation. They've been marked superseded with notes.

This matters because it changes what isolation experiments are testing. The correct frame is: standard causal transformer blocks, shared residual stream, and then ask what modifications at block boundaries do something useful.

## Local-learning residual: clearly negative

The first boundary-mechanism test in the corrected frame: stop-gradient at block boundaries + one local prediction head per block trained to predict the next block's incoming residual delta.

3-block standardized comparison on TinyShakespeare 100K/20K, 13 epochs, ~186K params:

| Variant | Best val LM loss | Best epoch |
|---|---:|---:|
| End-to-end 3-block | 1.644 | 10 |
| Local 3-block | 2.081 | 13 |

Gap: 0.437 nats. The gradient-boundary proof confirms the mechanism is real — lower blocks receive zero gradient from the LM loss and are trained only by their local heads. The mechanism works mechanically. The language model quality tanks anyway.

The output at epoch 13 says it plainly:

```text
local_3b epoch 13 sample
First Citizen:
Before we proceed the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the the
```

vs the end-to-end control at epoch 10:

```text
end_to_end_3b epoch 10 sample
First Citizen:
Before we proceed and the common and the people,
And the consul, and the people and the people,
And the people and the people and the people,
And the people and the people
```

The local heads are learning nontrivial predictions (block 3 learned MSE 0.97 vs zero-predictor baseline 8.27 on the overfit batch). The problem isn't that they're failing to learn — it's that isolated lower blocks, trained only toward predicting delta targets, don't develop representations useful for language modeling. The top block has to do everything with a residual stream that the lower blocks weren't trained to help.

See [`research/questions/local-learning-residual/README.md`](../questions/local-learning-residual/README.md).

## Attention-residual: marginal, probably noise

Second boundary mechanism: content-based attention over earlier block-boundary residual states for the same token position, inserted before the standard sequence attention and FFN. An internal control (same memory bank, token-independent learned mixing weights instead of content-based attention) was run alongside.

3-block standardized comparison, same frame:

| Model | Best val loss | Final val loss | Runtime (s) |
|---|---:|---:|---:|
| External control | 1.6435 | 1.6544 | 84.6 |
| Depth-only attention-residual | **1.6311** | 1.6574 | 112.4 |
| Internal control | 1.6456 | **1.6456** | 88.5 |

The depth-only model's best-loss edge is 0.012 nats — one seed, and it disappears by the end of training (final loss 1.657, worse than baseline's 1.654). The internal control, which exposes residual history without content-based selection, is essentially the same as baseline. The content-based selection adds nothing the dumb mixing doesn't also fail to achieve.

33% slower for no stable quality gain.

See [`research/questions/attention-residual/README.md`](../questions/attention-residual/README.md).

## Where this leaves the architecture vision

Two boundary mechanisms tested in isolation in the corrected frame. Both negative or marginal. Neither is a surprise in the sense that small-scale char-level LM is a harsh test — the baseline transformer is already quite good relative to the parameter budget. The architecture's potential value probably lies elsewhere: async or selective computation (not testing all blocks on every token), or behavior that only appears at larger scale where depth routing has something real to route. Both of those are larger bets than what's been tested so far.

## Async/selective execution: mechanism works, GPU doesn't cooperate

Learned per-token gating — each block decides independently whether to execute for each token. The gates do learn genuine selectivity; they don't collapse to all-on or all-off. The problem is purely execution: 15–32% fewer logical block executions produce 26–29% worse wall-clock time on the RTX 3090.

Per-token conditional execution breaks batched GPU parallelism. The overhead of branching across a batch — different tokens taking different paths — is larger than the compute saved by skipping. This isn't an implementation problem that tuning would fix; it's the shape of GPU execution.

See [`research/questions/async-selective/README.md`](../questions/async-selective/README.md).

GRU: 1.8–2.8× faster training, 2.5–3.7× faster decode vs transformer. LSTM: 1.4–2.5× faster training but falls behind transformer on decode at 10M params — that's an odd result worth keeping in mind. The structural advantage for RNNs is that decode cost is constant regardless of context length: no KV cache growth. At long context (256), LSTM and GRU VRAM stays flat while transformer VRAM grows; GRU decode is 3× faster than transformer at 10M/256 context.

## Causal triangle attention residual: negative

The depth-only attention residual (earlier today: 0.013 nat edge) was extended to attend over both depth and prior sequence positions in a 2D causal mask — attending the same position at earlier depths, and earlier positions at any depth. Mechanically verified: allowed reads affect output, forbidden reads don't.

| Model | Best val loss |
|---|---:|
| external_control | 1.639 |
| depth_only | **1.618** |
| causal_triangle | 1.667 |

The 2D variant is worse than both baseline and depth-only (+0.028 vs baseline, +0.049 vs depth-only). Runtime is 1.8× baseline. The depth-only signal was actually stronger this time — 0.021 nats vs 0.013 earlier — but extending it to sequence positions degraded rather than improved. More memory available ≠ better learning.

See [`research/questions/causal-triangle-attention/README.md`](../questions/causal-triangle-attention/README.md).

## Where the boundary mechanism search ended

All five experiments on the "modify transformer block boundaries" hypothesis are done:

1. **Local learning** — clearly negative (0.437 nat gap)
2. **Depth-only attention residual** — marginal (0.013–0.021 nat edge, inconsistent across runs)
3. **Async/selective execution** — mechanism works, GPU execution negates savings
4. **Causal triangle attention residual** — negative
5. **GPU utilization** — RNNs are 1.8–3.7× faster depending on configuration

The transformer-boundary approach hasn't produced anything at this scale. The GPU utilization result reframes what to try next: the interesting direction is "RNN + attention over history" — take the throughput advantage that's already confirmed large and real, then ask what you can add to make RNNs better at long-range recall. That's a different hypothesis family than where tonight started.
