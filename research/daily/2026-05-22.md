# 2026-05-22

Async execution cannot provide wall-clock speedup on a single GPU. This is not a tuning failure — it's architectural: GRU blocks are memory-bandwidth-bound, CUDA streams parallelize compute, and there's no compute to parallelize. The project's core async hypothesis is dead for single-GPU hardware.

## Async wall-clock: definitive negative

The last open question from Max's dictation today: "have we actually proved async-on vs async-off gives a wall-clock speedup?" Tested 3 execution strategies (sequential, parallel streams, async streams) across 9 configurations:

```json
// experiments/async_wallclock/artifacts/results.json (selected)
{"config": "4_blocks_64d", "sequential_ms": 24.78, "parallel_ms": 30.35, "async_ms": 36.11}
{"config": "8_blocks_128d", "sequential_ms": 124.24, "parallel_ms": 136.76, "async_ms": 145.35}
{"config": "8_blocks_512d", "sequential_ms": 1453.63, "parallel_ms": 1509.07, "async_ms": 1505.17}
{"config": "16_blocks_64d", "sequential_ms": 100.24, "parallel_ms": 117.21, "async_ms": 147.91}
```

| Scale | Sequential | Parallel | Async | Async/Parallel |
|-------|-----------|----------|-------|----------------|
| Small (4×64) | 24.78ms | 30.35ms | 36.11ms | 0.84× |
| Medium (8×128) | 124.24ms | 136.76ms | 145.35ms | 0.94× |
| Large (8×512) | 1453.63ms | 1509.07ms | 1505.17ms | 1.00× |
| Deep-narrow (16×64) | 100.24ms | 117.21ms | 147.91ms | 0.79× |

Sequential is **always** fastest. No configuration shows any benefit from multiple CUDA streams. Two failure modes with no sweet spot between them:

- **Small blocks:** stream/event management overhead dominates (16–22% slower than sequential)
- **Large blocks:** GPU memory bus saturates — a single kernel already uses all bandwidth, nothing left to overlap

## Inference pipelining: worse still

Autoregressive generation (batch=1, seq_len=1, 256 timesteps) — the scenario where async was supposed to shine:

From the [async-execution question report](../questions/async-execution/README.md#inference-regime-batch_size1-seq_len1-timesteps256):

| Config | Sequential | Async | Ratio |
|--------|-----------|-------|-------|
| 4×128 | 153ms | 283ms | 0.54× |
| 8×128 | 341ms | 1022ms | 0.33× |

Per-token tensors are tiny. Stream management overhead is catastrophic — async is 2–3× slower than just running sequentially.

## Why this is architectural, not implementational

GRU blocks have low arithmetic intensity (few FLOPs per byte moved). They're memory-bandwidth-bound. CUDA streams provide parallelism over compute resources, but when the bottleneck is the memory bus, launching kernels on separate streams means they compete for the same bandwidth while paying synchronization overhead. No implementation trick fixes this on a single GPU. Multi-GPU (each block on its own device with its own memory bus) remains theoretically viable but wasn't in scope.

## Project synthesis

Wrote [`research/SYNTHESIS.md`](../SYNTHESIS.md) — 83-line decision matrix covering all 18 experiments run across the project. The architecture produces language (+0.085 nats from transformer at matched params, gap closing with scale), mix-add norm control works, partial-detach N=4 gives 2.46× training speed at +0.041 nats cost. But the motivating hypothesis — that async execution enables a qualitatively different speed/quality tradeoff on available hardware — is conclusively falsified.

## Where this leaves the project

All experimental threads answered. The architecture is viable but strictly dominated by transformers at matched scale, and the async execution model that motivated it cannot deliver speedup on single-GPU hardware. Further work requires either new hardware (multi-GPU pipeline parallelism) or a new research direction from Max. The project reached its natural conclusion.
