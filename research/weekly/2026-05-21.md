# Week of 2026-05-19

Fixed multi-rate execution is the strongest positive result this project has produced: skip computation on a fixed schedule, reuse cached outputs, get **20.7% wall-clock speedup with better quality** than running every block every step. The rate constraint acts as a regularizer — blocks forced to produce outputs useful across multiple future timesteps learn longer-timescale representations. Diagonal connections looked promising on one seed, then catastrophically diverged on another — killed. Backend decided (PyTorch + torch.compile + Triton). Core code integrated. Literature confirms we're in well-mapped territory with a novel observation (fixed rates regularize, not just skip).

## Multi-rate execution: 20% free

Four blocks with rates [1, 2, 4, 8] — each successive block halves its execution frequency, reusing its cached MixAdd output on skipped steps:

| Step | All-rate-1 val loss | Multi-rate val loss | Delta |
|------|----:|----:|------:|
| 500 | 2.188 | 2.168 | -0.020 |
| 1000 | 2.062 | 2.051 | -0.010 |
| 2000 | 1.946 | 1.941 | -0.006 |

Timing: all-rate-1 73.89ms vs multi-rate 58.59ms → **20.7% speedup**. Quality advantage is consistent at every checkpoint. ([artifact](../../experiments/fixed_multi_rate/artifacts/aggressive_1248/report.json))

The conservative variant [1,1,2,4] shows the same pattern at smaller magnitude: **14.8% speedup**, -0.010 nats quality improvement ([artifact](../../experiments/fixed_multi_rate/artifacts/short_run/report.json)).

Pushing further to [1,2,4,8,16]: ~22% speedup but quality degrades (+0.016 nats). This locates the boundary — rate-16 blocks compute too rarely to track the data at this sequence length.

**Why this works where selective execution failed:** learned gating was 26-29% *slower* — decision overhead exceeded savings from skipping cheap blocks. Fixed schedules have zero decision cost; the full compute reduction is wall-clock savings.

**The regularization interpretation:** a block that only executes every 4th step must produce output that remains useful for the next 3. This pressure toward temporally-stable representations apparently helps generalization. The effect is small but consistent (negative delta = multi-rate wins at every measured point for [1,2,4,8]).

## Diagonal connections: confirmed negative

Multi-seed replication of the suggestive single-seed result:

| Seed | Control (2000 steps) | Diagonal | Delta |
|------|---:|---:|---:|
| 42 | 1.988 | 1.935 | **-0.052** |
| 43 | 1.934 | 1.934 | +0.000 |
| 44 | 1.959 | 18.386 | **+16.4 (diverged)** |

Seed 42 was lucky. Seed 43 showed zero effect. Seed 44 catastrophically diverged between step 1500 and 2000 while the control trained normally. The naive diagonal connection (block A's output delta at time t feeds block B at time t+1) is **unstable and unreliable**. ([artifact](../../experiments/fixed_multi_rate/artifacts/diagonal_1248_multi_seed/report.json))

A gated/scaled variant (learnable mixing initialized near zero) might stabilize it, but that's a different experiment — the naive version is dead.

## Residual streams across time: the architecture works

The Mon-Wed result that enabled everything above: a single transformer block reused across timesteps with causal temporal attention reaches val loss **1.670** — 0.038 nats from the transformer anchor at 2.6× the parameter count.

Three variants tested at d_model=192, temporal window k=4, 50K chars / 3 epochs ([experiment artifacts](../../experiments/residual_stream_time/)):

| Variant | Val loss | Stream RMS |
|---------|----------|-----------|
| No norm control | 3.29 | 1555 (explodes) |
| [Temporal LayerNorm](../../experiments/residual_stream_time/artifacts/scaleup-192-timestep-norm/) | 1.788 | 3.33 |
| [Learned mix-add](../../experiments/residual_stream_time_mixadd/artifacts/scaleup-192/) | 1.791 | 1.01 |

Extended to 100K/5ep: **1.670** val loss, still declining. Mix-add (learned convex combination `α·stream + (1-α)·new`) matches LayerNorm without any normalization layers. Trained α values: token entry ≈0.49, block update ≈0.88, temporal ≈0.93 — the model learns to be cautious at temporal injection.

## The async tradeoff, quantified

```
Full gradient:  val 1.670, 606s runtime
Stop-gradient:  val 1.894, 257s runtime  (+0.223 nats, 2.36× faster)
```

([full-grad artifact](../../experiments/residual_stream_time_mixadd/artifacts/extended-100k-5ep/tiny_metrics.json), [stop-grad artifact](../../experiments/residual_stream_time_stopgrad/artifacts/extended-100k-5ep/tiny_metrics.json))

Naive async (detach every step) is not free. The multi-rate result suggests a better path: don't break gradients within each block's execution — just execute blocks less often.

## Literature backing

30+ papers supporting our three directions. Key finding: our multi-rate result maps directly to Clockwork RNN (Koutnik et al. 2014) but with a novel observation — fixed deterministic rates *regularize* (quality better, not just equivalent). Stochastic Depth (Huang et al. 2016) and Mixture-of-Depths (Raposo et al. 2024) are the closest comparisons for the "skip computation" pattern, though both use stochastic/learned selection rather than fixed schedules. ([full review](../questions/literature-backing/README.md))

## Async hardware: corrected understanding

The previous "decisive negative" for async execution only tested PyTorch's high-level streams API — the wrong tool. The RTX 3090 (GA102, 82 SMs) hardware does support concurrent kernel execution: different SMs can run different kernels simultaneously via persistent kernels, fused blockIdx dispatch, or CUDA Graphs. This is an open research path, not a closed door. ([corrected README](../questions/async-execution/README.md))

## What remains open

- **Parameter efficiency.** 2.6× params for similar quality. Tunable or fundamental?
- **Async via multi-rate.** Multi-rate speedup doesn't require gradient detach. Can these compose — multi-rate + stop-grad on slow blocks — for larger speedups with acceptable quality cost?
- **Scale.** All results are at d_model=192, 50-100K chars. Do they hold at larger model/data scale?
- **Gated diagonal.** Naive diagonal is dead. A learned-mixing variant initialized near zero might stabilize it — untested.
- **Matched-FLOP comparison.** Does multi-rate beat a deeper all-rate-1 model given equal compute? Experiment designed, launches after midnight. This is the critical "is it real?" test.
- **True hardware async.** Persistent kernels / CUDA Graphs for running blocks on different SMs simultaneously. Research path identified, not yet attempted.

## Honest assessment

The best week yet, with a healthy dose of humility. Multi-rate execution is real and robust — 20% wall-clock speedup with a consistent quality advantage across two rate configurations, multiple checkpoints, and a clean mechanistic story (rate constraint → temporal stability → regularization). The literature confirms we're in Clockwork RNN territory with a genuinely novel observation about deterministic rates regularizing.

The diagonal result is the week's most important *negative*. One seed looked spectacular (-0.052 nats); multi-seed showed it was luck plus instability. This is exactly the kind of result that could have wasted weeks if not replicated immediately. The multi-seed rule exists now because of this failure.

The backend question is resolved (PyTorch + torch.compile + Triton), core code is integrated and compile-compatible, and the async hardware path is reopened with a corrected understanding of what the GPU can actually do.

The critical open question going into next week: the matched-FLOP experiment. Multi-rate gives 20% speedup — but is that because skipping is genuinely better than computing, or because the all-rate-1 baseline is wasting compute on blocks that don't help? If a deeper all-rate-1 model using the same total FLOPs matches multi-rate quality, then multi-rate is just an efficiency trick. If multi-rate still wins, the rate constraint is doing something structurally useful. This test launches tonight.
