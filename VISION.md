## The final model

An ultra-flexible model architecture that runs performantly on an RTX 3090 at comparable performance to other options.

Along the way: validate, debunk, and experiment with Max's intuitions and visions for what that architecture should look like — even if we don't end up at it inevitably. Explore directions where other people haven't explored before. But if they have, repeat those experiments and build baselines so we know we're not going deep into the woods from nothing.

## What the model should DO

- **Character-level language generation.** Type at it, see what it generates. Interactive inference.
- **Learn useful representations across multiple timescales** — fast features and slow abstractions coexisting.
- **Remain competitively capable relative to transformer baselines** at matched compute. Not sacrificing accuracy for novelty.
- **Support dynamic computation** — variable effort per token at inference (think longer on hard tokens, skip easy ones).
- **[Stretch] Multi-token prediction** — predict further ahead when confident, dynamically choosing how many tokens to output per step.
- **[Stretch] Arbitrary-order prediction** — predict tokens/patches in any order, choose optimal sampling order at inference. Connects to Max's master's thesis work.
- **[Stretch] Multi-modal** — images (arbitrary-order patches), eventually image+text unified.

## What kind of system it should BE

- **Fast on an RTX 3090.** Wall-clock speed is the primary metric — not theoretical FLOPs, not parameter count alone. If it doesn't give wall-clock speedup, we're not doing it right yet.
- **All active parameters resident in GPU memory.** Process activations in place rather than swapping.
- **Many small modules rather than one monolith.** Width over depth. Blocks that can be added, removed, rearranged.
- **Avoid unnecessary synchronization between modules.** Blocks should not need to wait for each other.
- **Multi-timescale processing.** Some modules iterate rapidly, some update infrequently, naturally developing hierarchical abstraction.
- **Locally trainable** — or at minimum, neighborhood-locally trainable. Less gradient coupling = more modularity. Full global backprop is what we're trying to reduce or eliminate.
- **Small, understandable, inspectable.** Max wants to understand what it's doing, not use it as a black box. Look at outputs, not just loss curves.

## Architectural character

These are strong preferences that shape the design space, not absolute requirements:

- **Feedforward blocks** (single residual blocks), not thick RNN stacks with internal hidden state. Later, internal state may be added.
- **No stock RNN mechanisms** (GRU, LSTM) unless explicitly compared against the ideas here.
- **No layer norm / batch norm** where avoidable — prefer mix-add or orthogonal parameterization for norm management.
- **Diagonal information propagation** — connections across time AND depth simultaneously. The interesting structure is the graph of interactions over spacetime, not a single chain.
- **Predictive / self-predictive organization** — blocks predicting their own inputs, producing messages that help neighbors predict well.
- **Mix-add residual stream** — `mix(a, b, m) = a * sqrt(σ(m)) + b * sqrt(1 - σ(m))` for norm-preserving residual connections. Learned, not fixed.

## Datasets

**Primary:** Character-level English (Karpathy-style). After training, the model should be interactive.

**Stretch:** Arbitrary-order image patches (from Max's master's work). Images split into patches, any ordering at training, optimal order at inference. Return to this after the core architecture works.

**Later:** Structured prompt-space text. Image-text unified.

## Non-goals

- Academic novelty or publication
- Beating benchmarks
- A large codebase
- Architectural decisions made by intuition and never tested
- Black-box complexity

## Open tensions

These are real tensions the architecture must navigate, not problems to solve in this document:

- Speed vs quality — how much accuracy can we trade for wall-clock performance?
- Locality vs learnability — does reducing gradient coupling kill learning, or does it force useful structure?
- Flexible computation vs stable training — dynamic depth/token count adds complexity to training
- Graph richness vs communication bottlenecks — if every block cheaply reads every other, the graph is decorative and async is meaningless
- Inductive bias vs generality — multi-rate is an inductive bias; is it the right one?
